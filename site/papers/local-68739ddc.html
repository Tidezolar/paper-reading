Grounding AI Agents in Contracts: An Empirical Evaluation of Spec-Driven Test Generation

Abstract（原文）

展开 / 收起 Abstract 原文
LLM-based agents are increasingly used for coding tasks, where they have outperformed many classical approaches and scaled to repository-level tasks, such as test generation. However, when di- rectly prompted to generate tests, these agents can fail to reason about the code and its underlying contracts, thereby missing edge cases and behavioral boundaries that affect test quality. To address this limitation, we propose Spec-Driven Test Generation, where we instruct an agent to first reason about – and explicitly document – code pre-conditions, post-conditions, and undefined behaviors. This intermediate semi-formal specification acts as a cognitive scaffold to guide subsequent test generation. Our evaluation on production bugs from Google shows that the spec-driven agent can deliver a 9.8 percentage points (p = 0.0352) improvement in bug detection rate and a 2.5 percentage point (p = 0.0034) improvement in branch coverage, compared to a traditional test generation agent baseline. Using LLM-as-a-Judge, we further show that test suites generated by the spec-driven agent are superior to the baseline and human-authored tests in 77.8% and 56.7% of the cases, respec- tively, and demonstrated improvements on following best practices, readability, and edge-case coverage.

研究背景

生成可编译、可通过的单元测试已经较容易，真正困难的是写出能区分正确行为与错误行为的测试判定依据（oracle）。直接读代码生成测试时，智能体可能停留在正常路径，遗漏输入边界、异常条件和状态副作用。设计契约为这些行为提供了表达方式，但已有系统通常缺乏可直接使用的契约，因此作者让智能体先从代码与上下文中提炼契约，再据此生成测试。

研究目标

在相同模型与工具框架下，强制智能体先生成包含前置条件、后置条件与测试建议的半形式化文档，能否比直接生成测试更有效地覆盖分支并检出真实历史缺陷？生成文档是否写到了该缺陷违反的约束，又有多少约束能够转化为有效测试？

研究内容

  1. 把行为要求写成中间产物：为函数、方法和类建立 $S_c=\langle D_c,Pre_c,Post_c,Sug_c\rangle$，分别记录行为描述、执行前约束、执行后保证与对应测试建议；条件使用自然语言，落盘为 .spec.md。
  2. 用修复后代码进行盲测生成：选择 Google 内部 90 个历史缺陷，每个方案各尝试 5 次；提供修复后代码并移除目标组件既有测试，隐藏缺陷描述、提交说明和修复差异。两组均使用 Gemini 3 Flash，实验跳过人工契约修订。
  3. 通过版本回退验证缺陷检出：测试须先在修复版通过，再在回退后的缺陷版触发运行失败；同时统计分支覆盖，用 Gemini 3.1 Pro 多次评审测试质量与目标缺陷的契约覆盖情况。

主要结论

  1. 五次尝试提高历史缺陷检出率：detect@5 从 53.4% 升至 63.2%，增加 9.8 个百分点，McNemar $p=0.0352$；单次仅从 36.9% 升至 41.1%，差异不显著。五次运行实际检出缺陷为 48 个与 57 个。
  2. 收益主要体现在分支与边界行为：平均分支覆盖率由 46.4% 升至 48.9%，$p=0.0034$；行覆盖率从 74.8% 降至 74.4%，差异不显著。两组 pass@5 均为 98.9%。
  3. 契约覆盖与检出相关，转化仍有损耗：450 次尝试中，写到目标契约时检出率为 151/275=54.9%，未写到时为 34/175=19.4%；这是相关性分析。即使写对契约，仍有大量输入构造、场景落实和断言失败。
  4. 质量偏好伴随额外成本：LLM 评审报告相对基线总体胜率 77.8%，相对人工测试 56.7%；总 token 从 243.9M 增至约 336.7M（+38%），每个检出缺陷的 token 成本约增加 16.2%。

显式契约提供了一个可检查的语义中间层，使失败可以分解为“未提取关键约束”和“约束未落实为有效输入及断言”。执行结果支持整套两阶段流程在该历史缺陷任务上的收益；契约本身的独立因果贡献仍需等预算、等长度的计划或伪代码对照。契约覆盖率只评估是否命中一个已知缺陷对应的约束，不能据此断言整个组件的规格完整或正确。

分章节总结与分析

Abstract

p.1
本节总结

提出先记录代码的前置条件、后置条件与未定义行为，再生成测试的两阶段流程。摘要概括90个工业历史缺陷上的9.8个百分点检测增益、2.5个百分点分支增益及模型质量偏好。

研究关联与分析

摘要压缩了实验边界。9.8个百分点对应k=5，56.7%来自LLM对人工测试的偏好；单次尝试、等预算收益与人工工程质量等效需要分别核实。

1

Introduction

p.1
本节总结

引言将测试生成难点归于缺少预期行为的显式锚点：模型可执行代码并生成表面测试，却可能漏掉边界。作者借鉴Design by Contract，让智能体先写半形式化规格，并把规格驱动流程、契约覆盖率和工业评估列为贡献。

研究关联与分析

引言建立了“表达约束→更有针对性的测试→更多缺陷检出”的机制假设。后文直接比较的是整套流程；认知支架的独立作用尚未通过等预算或其他结构化计划消融识别。

2

Semi-Formal Specifications for API behavior

p.2
本节总结

定义每个代码单元的规格为 $S_c=\langle D_c,Pre_c,Post_c,Sug_c\rangle$，包含意图、前置条件、后置条件和测试建议。条件用自然语言写入.spec.md，可标记已测/未测并关联测试。作者认为注释、文档与调用点可帮助推断开发者意图；客户数据库示例展示空姓名异常缺少测试时如何产生建议。

研究关联与分析

形式化元组规定了文档结构，未使自然语言条件自动可判定，也未证明它们与需求一致。测试建议有助于连接约束与代码，但错误意图、过度规格和条件遗漏仍需外部检查。示例允许已有测试；实际greenfield评估移除了目标既有测试，应区分框架功能与实验条件。

3

Proposed Approach

p.2
本节总结

总览把输入代码经由规格提取与测试生成转化为测试套件。Listing 1中，已有无效电话和成功路径测试，空姓名错误条件被标为未测并给出具体建议；该可读文档承担中间计划作用。

研究关联与分析

该节展示预期工作流和示例，没有新增效果实验。文本中的“空姓名→异常”说明为什么中间产物能被审核；规格可审阅性与实际审核收益仍是不同命题，后者未在自动化实验中测量。

3.1

Phase I: Specification Extraction

p.3
本节总结

第一阶段依次聚合上下文、推断前后置条件、对照可用测试标记覆盖、为未测条件生成建议。目标覆盖所有公共、私有方法及辅助函数，形成完整的代码单元规格集合。

研究关联与分析

覆盖全部方法依赖提示，作者明确说未程序化强制覆盖。后文35次方法遗漏与这一设计缺口呼应。适用时可通过代码符号清单检查契约条目，但这属于改进建议，原方法没有实施证据。

3.2

Human-in-the-Loop Specification Curation

p.3
本节总结

在规格完成后，开发者可修改条件并接受、拒绝或修订测试建议，再进入代码生成。该环节利用了规格的人类可读性。

研究关联与分析

这是框架支持的可选接口；§4.2的比较跳过人工干预。因此不能将实验效果归因于专家校正，也不能据此估算人工审核所需时间或收益。

3.3

Phase II: Oracle-Driven Test Generation

p.3
本节总结

第二阶段以规格和现有测试为输入，依次落实未测条件对应的建议，完成输入构造、单元断言、构建及验证。生成测试之前必须完成规格，使上下文包含显式边界条件。

研究关联与分析

执行建议仍需要解决可达性、复杂fixture与严格断言。后文110次测试阶段失败表明写出契约不保证生成可检出测试。一般流程描述为扩充既有测试，实验则从空目标重建，两者推广范围不同。

4

Empirical Design

p.3
本节总结

提出四个研究问题：缺陷检测与覆盖、测试质量、契约准确性和token成本。研究选择真实工业故障，以检验隐式状态依赖与边界违反，而非只看生成代码是否通过。

研究关联与分析

四类证据互相补充：执行指标约束效果，评审指标描述偏好，规格分析提供诊断，成本约束实用性。需要保持不同样本单位，特别是按bug聚合结果与逐次尝试标签的区别。

4.1

Dataset Collection

p.4
本节总结

数据来自Google内部问题系统，含90个已确认且可复现的历史修复，语言含C++、Java、Python、Go。仅保留单生产源码文件、相应测试及可选BUILD更改，排除语法小修、多媒体和个人信息问题。

研究关联与分析

真实缺陷增强实际语义复杂性；单文件、可复现、可识别测试目标的筛选也限制外推。缺少语言分布、领域分层及候选流失统计，多语言存在不足以证明各语言上的效果一致。数据私有降低独立复核能力。

4.2

Agent Configurations

p.4
本节总结

两组共用Gemini 3 Flash、相同工具与推理参数（T=1.0、TopP=1.0、TopK=50）。基线分析源码、写测试并运行验证；规格组增加强制的规格阶段。为减少人工混杂，两组比较中跳过HITL。

研究关联与分析

模型、工具控制使比较具备清楚的流程层解释；规格组额外使用token，尚未控制计算量与结构化内容的区别。基线也具备推理能力，不能把它理解为完全没有计划或思考的单次代码补全。

4.3

Greenfield Test Generation Setup

p.4
本节总结

生成端只得到修复后源码 $C_f$ 与空测试目标。隐藏缺陷描述、提交信息和修复diff；先运行生成测试验证修复版通过并记录覆盖，再反向应用补丁得到 $C_b$。只有测试在修复版通过、在缺陷版运行失败才算检出，编译失败排除。

研究关联与分析

协议隔离已知bug信息并提供可执行真值，能检验测试对历史行为差异的敏感性。模型读取修复后实现已获得正确行为的重要线索；该结果对未知bug源码上的独立oracle恢复与新缺陷发现没有直接结论。文中目标测试移除不等同于整个仓库所有辅助上下文均不可见。

4.3.1

Post-execution sanity checks

p.5
本节总结

运行后审计文件操作，修改被测源码或其他既有源码的尝试被丢弃且不补跑；只允许改目标测试和必要BUILD。两组都允许创建规格、草稿和任务清单等临时文件。

研究关联与分析

审计避免智能体篡改被测代码制造虚假故障，但被剔除运行数量及其分母处理未明确。两组均可写规格表明主要处理差异是强制流程与指令，不能简单归为一组拥有文档工具、另一组没有。

4.4

Evaluation Protocol and Metrics

p.5
本节总结

该父节组织定量指标、质量评审和契约评审三个小节，本段本身只含标题。具体定义与统计过程在随后小节展开。

研究关联与分析

保留原始层级以免将后续小节误当独立主节。该段没有独立证据；评估有效性需结合4.4.1–4.4.3的输入、单位与标签定义判断。

4.4.1

RQ1: Quantitative Effectiveness

p.5
本节总结

每个缺陷每组独立采样5次。pass@k衡量修复版可通过性；detect@k衡量k次内得到有效故障测试的概率；另统计行、分支覆盖。按90个bug进行10,000次bootstrap估计区间，检出采用McNemar，连续覆盖采用配对Wilcoxon。

研究关联与分析

以bug为bootstrap单位避免把所有运行当完全独立任务，但没有详细给出各k估计与列联表构建的完整实现。pass@k衡量存在可通过套件的机会，不等于正确性或发现bug的能力。多个k同时检验时也应考虑多重比较。

4.4.2

RQ2: Qualitative Test Rigor via LLM-as-a-Judge

p.5
本节总结

用更强的Gemini 3.1 Pro匿名成对评估，随机测试A/B顺序，比较最佳实践、可读性、边界覆盖与整体偏好。每维度5次调用严格多数投票，无多数视为平局；评分规则浓缩自Google测试实践，并同样比较人工测试。

研究关联与分析

随机顺序和重复投票降低位置偏差与随机噪声，不能直接校准质量真值。同系列模型可能共享风格偏好；边界评审与规格表述契合也可能使该维度偏向处理组。公开独立人工复核与分母、套件选择规则有助于解释胜率。

4.4.3

RQ3: Specification Accuracy and Contract Coverage

p.5
本节总结

定义ContractCoverage@k：k次规格中能否描述目标历史缺陷违反的行为约束。事后judge读取bug描述、提交说明、修复diff和规格，重复5次多数投票；另将失败分为规格遗漏或测试落实失败。作者明确该指标需要已知修复，且只覆盖目标缺陷相关边界。

研究关联与分析

生成端与评审端的信息权限必须分开：judge可看修复diff不代表智能体生成时看过。该指标是缺陷条件化的局部召回代理，没有完整契约集合的分母，也没有精度；一份包含大量幻觉的规格仍可能命中目标约束。

5

Evaluation Results

p.6
本节总结

该节开始报告工业研究结果，随后依次回答RQ1至RQ4，包括检测、覆盖、质量、规格诊断和token成本。

研究关联与分析

本父节只是结果入口，不单独提供数据。应按后续指标各自的统计单位与生成预算解释，避免把成本、模型偏好和可执行检出汇成一个“准确率”。

5.1

RQ1: Quantitative Effectiveness

p.6
本节总结

RQ1分成缺陷检出能力与结构覆盖，在k=1至5的独立尝试预算下比较两组，并先检查测试可运行性。

研究关联与分析

不同k共享同一批缺陷与生成样本，曲线上的各点并非独立复制实验。随着采样增加，优势扩大支持预算与流程可能存在交互，仍需等总成本曲线确认实际资源配置优势。

5.1.1

Test Suite Pass Rate (pass@k)

p.6
本节总结

表1的基线/规格组pass@1…5为94.4/94.2、98.0/97.8、98.4/98.3、98.7/98.7、98.9/98.9%。作者据此认为两组基本代码生成能力相当，契约阶段没有降低生成可运行测试的机会。

研究关联与分析

通过率几乎相等使“只是改善编译率”的解释不充分，但通过率属于饱和的有效性指标，不能仅凭它证明全部检出增益都由契约语义机制产生。高通过率也可能来自未覆盖关键行为的容易测试。

5.1.2

Fault Detection Rate (detect@k)

p.6
本节总结

表2中detect@1…5由36.9→41.1、45.3→51.3、49.4→56.6、51.8→60.5、53.4→63.2%，增益逐步扩大；p值为0.3075、0.4545、0.0574、0.0352、0.0352。k=5共同检出45个，规格独有12个，基线独有3个。极端难度（全部检出或全部失败）的bug从59/90降至52/90，作者解释为部分困难bug转入偶尔可检出状态。

研究关联与分析

显著性主要在k=4、5，不能把9.8个百分点当作单次收益。k=5的区间较宽：基线[43.3,63.3]%、规格[53.3,73.3]%。配对检验利用同一bug上的成败，区间重叠本身不否定差异。规格组未完全支配基线，3个独有缺陷表明两者探索仍有互补；“更难”解释来自样本内频率，未独立标注缺陷难度。

5.1.3

Structural Coverage

p.7
本节总结

覆盖率针对固定版本的目标源码，先对每个bug的5次运行取平均，再跨bug汇总。行覆盖74.8%→74.4%，p=0.3659；分支覆盖46.4%→48.9%，p=0.0034。作者认为规格更能引导边界与复杂控制流。

研究关联与分析

分支增加而行覆盖基本不变与更细的条件探索相容；覆盖变化仍无法单独证明缺陷发现的具体中介机制。此处报告的是平均单次套件覆盖，不是5套测试合并后可达到的覆盖率，不能拿它直接估算组合测试的覆盖上限。

5.2

RQ2: Qualitative Test Rigor

p.7
本节总结

质量比较涉及文中所称83个成功生成的测试对象，与基线及原始人工测试分别比较。作者报告五次评审的自一致性≥90%，平局≤5.6%。

研究关联与分析

这里的83与后续77.8%、56.7%等百分比缺少明确的分母对应关系，并且“test”是否指整套测试与选取哪次运行未充分说明。高自一致说明judge稳定，不说明与人类评审一致；结论应限定为模型偏好。

5.2.1

Qualitative Evaluation Results

p.7

本节总结

此处样本单位从每个bug切换为每次尝试。重复尝试共享同一个缺陷难度、代码和约束，聚类相关性会影响后续逐尝试统计推断，不能把450完全当独立缺陷。

5.3.1

Contract Coverage and Bug Detection

p.8
本节总结

ContractCoverage@1/2/5为61.1%、69.7%、78.9%。450次中目标契约覆盖275次，检出151次（54.9%）；未覆盖175次，检出34次（19.4%）。Fisher p=$3.62\times10^{-14}$、Phi=0.35。作者将缺契约仍检出的34次解释为结构覆盖或崩溃检查偶然触发。

研究关联与分析

这是观察到的中等相关性：易理解bug可能同时更容易写契约和测试。没有随机删除/替换契约或控制缺陷固定效应，不能把54.9%与19.4%的差直接当因果效应。目标契约覆盖后仍有124次未检出，说明表示到执行存在明显瓶颈；偶然触发的机制解释也缺乏逐例独立验证。

风险与局限

  1. 修复后代码边界：生成端看不到缺陷与 diff，但可读取已修复实现；该协议评估回归测试生成，对含未知缺陷源码的意图恢复与新 bug 发现没有直接实验。
  2. 额外计算混杂：规格组消耗 38% 更多 token；缺少等预算基线、等长度计划、伪代码或执行轨迹对照，无法分离契约结构、额外思考与更大测试套件的贡献。
  3. 规格准确性仅局部可见：Contract Coverage 检查一个历史缺陷对应的约束，没有测量所有正确契约的召回，也没有量化幻觉、过度约束或错误条件的比例。
  4. 评审偏差与样本口径：测试质量与契约标签均依赖 Gemini 系列 judge；多次自一致只说明稳定性。§5.2 提到 83 个成功生成对象，但百分比汇总分母及从多次尝试选择测试的规则缺少清楚说明。
  5. 统计层级与多重比较：每个缺陷有 5 次尝试，RQ3 的 450 个样本共享 bug 难度；逐尝试 Fisher 检验未体现这种聚类。表2同时比较多个 k，未见多重检验校正说明。
  6. 数据与外部效度：单组织、私有单仓库及单源码文件修复筛选限制推广；缺少公开样本与完整运行脚本，难以独立重现效应值。
  7. 数据污染论证不足：使用同一底模控制共同暴露风险，但不能彻底排除不同提示对记忆调用的差异；正文据此完全排除污染的表述偏强。

实验从修复后实现提取预期行为，检验历史缺陷回放能力；对含未知缺陷的当前实现直接提取契约，可能把错误行为固化进文档。样本局限于 Google 单仓库及单生产文件修复，质量和契约标签依赖同系列 LLM 评审，缺少等 token 预算对照与独立人工校验。

成本与复现条件

最小复现需要一组可重放的缺陷/修复版本、可删除目标测试的构建环境、保持源码只读的文件审计、覆盖率工具、模型工具框架，以及双版本执行测试的基础设施。按原设置，两组各 90×5 次生成，契约与质量评审还需每项重复 5 次；生成组总 token 约 580.6M（表4两组相加），评审开销是否计入未说明。

本文未提供的条件包括内部仓库与 issue 数据、完整提示、停止/重试策略、wall-clock 时间、美元费用、各语言依赖、被剔除运行数量与精确模型版本端点；不能据此承诺逐项复现。独立复现可在公开真实缺陷集实施相同回放协议，并加入等 token 基线、人工契约标注和按 bug 聚类的统计分析；这是后续设计建议。
